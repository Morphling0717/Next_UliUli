# 手机首页歌单首屏修复

2026-09-09，沿用 Mia 已有的屏幕宽度检测方式修复 `components/SongSystem.tsx`。修改状态初始化、effect 清理和 GlassCard 在停用动画时的复位，保留歌单界面、桌面动画、手机无 stagger 列表和 `/app` 的 `disableAnimation`。

## 原因与修改

首页的 `HomeClient` 静态导入 `SongSystem`，因此它参与服务端渲染。原代码在服务端将 `isMobile` 初始化为 `false`，在手机浏览器却立即初始化为 `true`，首屏在 `motion.div` 与普通 `div` 之间选中了不同分支，导致 hydration 警告。原注释所说的 `dynamic({ ssr: false })` 只适用于 `/app` 的另一个调用点。

现在两端统一从 `isMobile=false` 开始，挂载后的下一帧再检测宽度；保留 resize 监听，并在卸载时取消待执行的帧及监听。手机仍使用普通列表，避免数百行等待逐条动画。没有关闭首页 SSR，也没有隐藏或抑制 hydration 警告。

额外的长歌单测试发现，入场动画未完成时切为手机模式，移除 `whileInView` 可能留下卡片的中间透明度。`GlassCard` 现在在 `disableAnimation=true` 时显式设置 `opacity=1`、`y=0`，沿用零时长过渡完成复位。其他卡片默认未禁用动画，仍走原行为。

## 验证记录

验证在外接 SSD 的独立工作副本、依赖目录、合成数据库和浏览器配置中执行，原网站数据及生产服务器未修改。先在同一环境放回旧组件，再替换为修复后的组件进行对照。

仅修正初始状态的中间版本还曾在 400 首合成歌曲页面停留 37.9 秒后保留卡片透明度约 0.023，已保存失败截图，因此最终修复包含卡片复位；没有把“水合警告消失”单独当作全部通过。

旧组件在 390 × 844 首页复现 hydration 警告，空列表文字及父列表的计算样式 `opacity=0`；修复后完整刷新没有该警告，空列表和直到 GlassCard 的祖先均为 `opacity=1`。

完整结果及原始证据保存在 `/Volumes/2TB SSD/WindChime-validation/hydration-uliuli`。本次是前次 Docker 验证之后的独立修复；前次保留的 Docker 镜像不包含此后续改动，部署时需从更新后的本站源码重新构建。


最终检查：

- 空歌单与 400 首合成歌曲的手机首屏正常，无该 hydration 警告；第 400 行和外层卡片可见，搜索、清空搜索、分类通过。
- 767 / 768 像素切换后，手机普通列表与卡片的透明度均恢复为 1；桌面保留动画分支。精确在动画中途切回的额外采样因浏览器会话落到空白页而无效，未将其算作通过。
- `/app` 桌面打开、关闭、手机重开歌单面板通过，400 行及卡片可见；首页悬浮菜单实际展开。
- 两个组件定向 ESLint 通过；Node 20.20.2 的完整生产构建通过（17.9 秒），随后干净 `tsc --noEmit --incremental false` 通过（11.1 秒）。
