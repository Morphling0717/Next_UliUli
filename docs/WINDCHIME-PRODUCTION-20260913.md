## 本轮发现的问题及处理

### 1. 服务器只抓取 main，开发分支跟踪失败

第一次切换尝试受限于服务器原有的窄 fetch refspec：配置只抓取 `main`，创建目标开发分支的跟踪关系失败。

该次失败自动回到旧服务，**未执行数据库迁移**。之后补充目标分支的抓取及跟踪关系，保留原 `main` 引用不变，没有把开发提交写入 `main`。

复用部署流程时应先检查实际 fetch refspec、目标远端分支及目标提交；不要用一次 `git pull` 的结果推断当前运行镜像来源。

### 2. 首个新镜像把首页错误构建为 App Hub

`9673648` 镜像上线检查发现：访问 `/` 显示了 `/app` 的 App Hub。原因已定位为 Docker builder 的工作目录 `/app` 与 Next.js App Router 的 `app/` 目录重名：Webpack 的 roots 解析把 `/app/app/page.tsx` 误解析为 `/app/app/app/page.tsx`。

发现后立即回退到旧镜像。此次回退**保留已经完成加法迁移的数据库**，没有用旧备份覆盖现有数据库，避免回退代码时丢失新写入。

修复提交 `89a3468`：

- 仅将 builder 工作目录调整为 `/build`，并修正从 builder 复制产物的路径。
- runner 工作目录仍为 `/app`，数据库仍为 `/app/data/codes.db`；生产数据和资源挂载路径不变。
- 在 Docker 构建中加入 `node scripts/verify-build-routes.cjs`。它只检查构建元数据和入口文件摘要，不加载路由模块或打开数据库。
- 构建检查要求 `/` 保持动态，且 `/` 与 `/app` 对应独立、不同内容的编译入口。
- **已经对旧失败镜像执行检查，确认检查器实际拒绝了错误产物**；不是只对正确样例运行一次。

`89a3468` 镜像构建及检查器均通过；切换前已在隔离容器中通过真实浏览器确认原主站画面。最终上线后再次核对 `/` 与 `/app`，两者内容和缓存行为正确。

## 可复用的安全部署步骤

1. **先确定实际运行来源。** 记录当前容器镜像 ID、仓库分支与提交、未提交改动、fetch refspec、实际挂载的绝对源路径、环境配置存在性和代理入口。完整记录留在服务器私密目录，不打印或提交秘密。核对旧分支是否有目标分支没有的功能。
2. **先备份，再改变运行服务。** 使用 SQLite 一致备份，或停写后完整保存数据库及相关 WAL/SHM；同时保留原环境配置、原镜像、私有媒体和服务器全部自有公共资源。不要只备份 Git 跟踪的图片，也不要复制正在写入的单个 `.db` 充当一致备份。
3. **不要盲运行服务器的 `upgrade.sh`。** 先审查它的分支、覆盖、删除、迁移和重启行为；旧脚本可能与本轮的目标分支及数据保护要求不一致。
4. **不要直接运行默认备份清理。** 本仓库 `scripts/backup-db.js` 默认只保留最近 20 份匹配备份，还会写入 `global_config` 的备份元数据。此次保留数据验证不能忽略这些副作用。确需复用该脚本时，使用独立备份目录并显式设置 `DB_BACKUP_RETENTION=0`，且把元数据变更纳入核对；不能让部署顺手删除服务器原有备份。
5. **用干净源码构建镜像。** 从已核对提交导出源码，使用固定 vendor 包与 lockfile。禁止将包含正式 `.env`、数据库、私有媒体的生产目录直接当构建上下文；不能只依赖 `.dockerignore` 恰好排除了所有敏感文件。
6. **使用副本验证迁移和新镜像。** 在隔离数据库副本连续迁移两次，检查完整性、原表逐行摘要及业务关联。测试实例仅绑定本地临时端口，使用隔离配置和合成内容；不要把测试实例同时连接到正式数据库。
7. **验证首页及关键业务后再切换。** 构建时执行 `scripts/verify-build-routes.cjs`；运行时分别检查 `/`、`/app`、`/mail`、`/mail/live`、健康接口和风铃 capabilities。正常的 HTTP 200 不足以证明页面内容正确。
8. **正式切换保留原绝对挂载。** 保留原有 16 项环境配置值、哈希盐、数据目录和自有资源路径。不要在新 release 目录直接套用旧 Compose 的相对卷，否则可能挂载新的空目录。新只读授权与连接密钥接口不要求部署 B 站网关。
9. **切换后重新核对。** 检查进程健康、实际镜像、首页内容、旧功能、`features.connectionKeys`、匿名管理接口拒绝访问，以及资源摘要和原业务数据。不得为了验收在生产生成合成信件或测试授权。

## 回退步骤

1. 先停止失败的新服务，保留故障证据和当前数据库的一致备份，避免两个版本同时写同一个 SQLite 数据库。
2. 优先恢复已保留的旧镜像及其原运行配置，继续使用原绝对挂载。不要把旧镜像回退和数据库恢复捆绑执行。
3. 如果已确认迁移为加法且旧代码兼容，应保留当前数据库；本轮首页故障就是这样回退的。
4. 只有确认数据库本身受损或确需不兼容迁移回退时，才在停止所有写入后，按审查过的方案恢复数据库及对应媒体。恢复旧备份可能丢失备份后写入，必须先核对并处理这些差异。不要手动删表、删列或用旧 `.db` 直接覆盖正在运行的数据库。
5. 回退后重新验证旧首页、健康接口、业务计数及公共资源；保留目标开发分支和原 `main` 的独立引用。
